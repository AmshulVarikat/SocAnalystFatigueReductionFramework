## Overview

This framework processes security alerts generated by a simulation environment (like Wazuh) and performs a series of contextual enrichments, risk scoring, classification, and grouping. The primary objective is to significantly reduce SOC (Security Operations Center) analyst fatigue by improving alert prioritization accuracy, reducing false positives, and consolidating related alerts into actionable investigation queues.

## How it Works: Architecture & Pipeline

The framework operates through a strict, 6-stage hierarchical pipeline. It takes raw, disparate alerts and transforms them into high-fidelity, context-rich investigations.

### Inputs
The framework consumes raw datasets typically stored in the `CodeSamples/` directory, including:
1. **Raw Alert Dataset**: JSON logs containing Wazuh-generated alerts (Rule ID, timestamp, source host, raw event data).
2. **Asset & Threat Intel Data**: Contextual data used to enrich raw alerts with criticality and reputation.

### The Pipeline Stages
1. **Ingest & Normalization**: Receives raw alerts, detects their source, and normalizes them into a canonical schema for consistent downstream processing.
2. **Alert Enrichment**: Attaches vital contextual information to each alert from external databases:
   - *Asset Enrichment*: Adds criticality, asset type, and business function.
   - *Threat Intelligence*: Adds indicator reputation and confidence scores.
   - *MITRE Enrichment*: Maps techniques, names, and categories.
3. **Risk Scoring**: Calculates a context-aware risk score (0-100) instead of relying solely on raw severity. Factors include asset criticality, threat intelligence, and MITRE mapping.
4. **Alert Classification**: A rule-based engine categorizes alerts into actionable buckets (`Likely Benign`, `Likely False Positive`, `Requires Investigation`, `Critical Incident`).
5. **Alert Grouping & Storage**: Groups related alerts (same host/user/rule) into a single context. Stores processed alerts into a high-performance SQLite database (`alerts.db`).
6. **Correlation Engine**: Analyzes the processed alert stream sequentially to group temporally and contextually related alerts into unified active investigations. Managed dynamically via rolling timeouts and customized JSON rule definitions.

### Outputs
- **SQLite Database (`alerts.db`)**: Persistent storage of all classified alerts and active investigations.
- **Log Files**: Each pipeline stage generates its own detailed log file in the `outputs/<stage_name>/` directory.
- **Web Dashboard**: A React-based interface for instant, real-time tracking of investigations and alerts.

## Getting Started

### 1. Clone the Repository

```bash
git clone https://github.com/AmshulVarikat/SocAnalystFatigueReductionFramework.git
cd SocAnalystFatigueReductionFramework
```

### 2. Environment Setup (Backend)

Ensure you have Python 3.8+ installed. It is recommended to use a virtual environment:

```bash
python -m venv .venv
source .venv/bin/activate  # On Windows use: .venv\Scripts\activate
pip install -r requirements.txt # Or install fastapi uvicorn etc. manually if not present
```

### 3. Environment Setup (Frontend Dashboard)

The dashboard is built with React, TypeScript, and Vite. You need Node.js installed.

```bash
cd Implementation/dashboard
npm install
```

---

## How to Fully Launch the Project

To run the full framework including the backend API and the frontend dashboard, you need to start both services.

### Terminal 1: Start the Backend API

This serves the `alerts.db` data to the dashboard.

```bash
# From the root of the project
source .venv/bin/activate
uvicorn Implementation.api.main:app --reload --port 8000
```

### Terminal 2: Start the Frontend Dashboard

This launches the React application.

```bash
# From the root of the project
cd Implementation/dashboard
npm run dev
```

The dashboard will typically be available at `http://localhost:5173`. You can view active investigations, alert trends, and detailed deep-dives into correlated events.

## Testing the Pipeline Manually

The framework relies on a central controller called `orchestrator.py`. You can test individual stages of the pipeline directly.

```bash
PYTHONPATH=. python Implementation/orchestrator.py
```

To test different stages of the pipeline, open `Implementation/orchestrator.py` and uncomment the desired test method at the bottom of the file (e.g., `orchestrator.test_stage_1_replay()`, `orchestrator.test_stage_6_correlation()`, etc.).

## Customizing Rules

The framework is highly modular. Both the Classification and Correlation engines rely on external JSON files, meaning you can alter the system's behavior without writing any Python code.

### 1. Classification Rules

**Location:** `Implementation/classification/rules.json`

This file determines how an enriched alert is binned into a category based on its risk score or specific indicators.

**Structure & How to Write:**
```json
{
  "numeric_thresholds": {
    "Critical Incident": 80,
    "Requires Investigation": 40
  },
  "absolute_overrides": {
    "threat_intel": ["malicious"],
    "mitre_tactics": ["credential access"]
  },
  "false_positive_indicators": ["5716", "1002"],
  "benign_indicators": ["192.168.1.100"]
}
```
*   **`numeric_thresholds`**: Triggers based on the calculated risk score.
*   **`absolute_overrides`**: Instantly forces a classification (e.g., if threat intel is "malicious", it's automatically an issue).
*   **`false_positive_indicators` / `benign_indicators`**: Exact string matches (Rule IDs, IPs) that bypass other logic to filter out noise.

### 2. Correlation Rules

**Location:** `Implementation/correlation/rules.json`

This engine defines how individual alerts are grouped together into a massive, tracked investigation. It tracks lateral movement, kill chain progression, and outbreak spread.

**Core Concepts for Writing Rules:**
*   **`anchor`**: The exact criteria to *start* a new investigation.
*   **`pivot_fields`**: Graph-based correlation. The engine learns new entities (IPs, users). If a new alert shares an entity with the running investigation, it gets pulled in.
*   **`track_progression`**: Tracks if the attacker is moving through the kill chain (e.g., tracking `mitre_tactic`).
*   **`match_criteria`**: Strict linear matching (e.g., *must* be the exact same `hostname`).
*   **`rolling_timeout_minutes`**: How long to keep the investigation open listening for events.

#### Example 1: Widespread PowerShell Network Connections
```json
{
  "rule_name": "Widespread PowerShell Network Connections",
  "anchor": { "rule_id": "92037" },
  "pivot_fields": ["rule_id"],
  "track_progression": ["hostname", "user_name"],
  "rolling_timeout_minutes": 120,
  "historical_window_minutes": 120
}
```
*How it works*: Any alert with rule `92037` starts this investigation. It then pivots on the `rule_id`, grouping *all* `92037` alerts, while actively tracking which new `hostname`s and `user_name`s are getting hit over a 2-hour window.

#### Example 2: Host-Based MITRE Kill Chain Progression
```json
{
  "rule_name": "Host-Based MITRE Kill Chain Progression",
  "anchor": { "classification": "Requires Investigation" },
  "match_criteria": ["hostname"],
  "track_progression": ["mitre_tactic"],
  "rolling_timeout_minutes": 120,
  "historical_window_minutes": 120
}
```
*How it works*: Starts when a host generates a "Requires Investigation" alert. It strictly matches on that exact `hostname` and tracks the `mitre_tactic` field. As the host throws new alerts with different MITRE tactics (Initial Access -> Execution -> Persistence), the investigation priority skyrockets.

#### Example 3: Malware Outbreak Detection (Hash Pivoting)
```json
{
  "rule_name": "Malware Outbreak Detection (Hash Pivoting)",
  "anchor": { "classification": "Critical Incident" },
  "pivot_fields": ["file_hash", "hostname", "src_ip"],
  "rolling_timeout_minutes": 180,
  "historical_window_minutes": 180
}
```
*How it works*: Starts on a "Critical Incident". It pivots heavily. If it sees `file_hash_A` on `Host_1`, it groups it. If it later sees `file_hash_A` on `Host_2`, it groups it. If `Host_2` then connects to a bad `src_ip`, it pulls that in too. It autonomously maps the outbreak across the network.
