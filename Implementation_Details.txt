Context-Aware Alert Prioritization Framework Specification
Purpose
This document describes the research framework responsible for processing security alerts generated by the simulation environment.
The framework consumes previously generated datasets and performs alert enrichment, risk scoring, classification, grouping, prioritization, and evaluation. Its objective is to reduce SOC analyst workload while improving prioritization accuracy and investigation effectiveness.
 
Framework Inputs
The framework consumes four datasets produced by the simulation environment.
1. Alert Dataset
Contains Wazuh-generated alerts collected during simulation.
Example fields:
•	Alert ID
•	Timestamp
•	Rule ID
•	Rule Severity
•	Alert Description
•	Source Host
•	MITRE Mapping
•	Raw Event Data
Purpose:
Provides the primary security events that will be analyzed and prioritized.
 
2. Asset Inventory Database
Contains metadata describing organizational assets.
Example fields:
•	Asset ID
•	Asset Type
•	Criticality Score
•	Department
•	Business Function
Purpose:
Provides business context required for risk scoring and prioritization.
 
3. Threat Intelligence Database
Contains indicators of compromise and reputation information.
Example fields:
•	Indicator
•	Indicator Type
•	Reputation
•	Confidence Score
Purpose:
Provides threat context for enrichment and risk evaluation.
 
4. Ground Truth Dataset
Contains expected classifications associated with alerts or simulated attack activities.
Example fields:
•	Alert ID
•	Expected Classification
•	Malicious / Benign Label
Purpose:
Provides an objective basis for evaluating framework effectiveness and measuring classification accuracy.
 
Framework Outputs: 
The framework outputs in 2 methods, instant reading and document output
-	Web interface for instant and immediate tracking of alerts in real time
-	PDF output for later reference and paper drafting
 
Framework Processing Pipeline
The framework processes alerts using the following pipeline:
Alert Dataset
      │
      ▼
Replay Engine
      │
      ▼
Alert Enrichment
      │
      ▼
Risk Scoring
      │
      ▼
Alert Classification
      │
      ▼
Alert Grouping
      │
      ▼
Prioritization
      │
      ▼
Analyst Evaluation
Each stage receives the output of the previous stage and adds additional context or analysis.
The final output is a prioritized investigation queue that can be compared against a baseline workflow to measure analyst workload reduction and prioritization effectiveness.
 
Framework Goals
The framework must support evaluation of the following research objectives:
•	Reduction of analyst workload
•	Reduction of false positives
•	Improvement of alert prioritization
•	Improvement of investigation completeness
•	Improvement of alert classification accuracy
•	Effective use of asset criticality information
•	Effective use of threat intelligence information
The framework should remain modular so that alternative scoring methods, classification methods, enrichment sources, and prioritization strategies can be evaluated independently.


*Continuing Phase numbering from Simulation Doc
Phase 6: Replay Engine
Purpose
Replay alerts into the research framework.
The replay engine simulates SOC alert queues.
 
Supported Replay Modes
Sequential Replay
Alerts replayed in order.
 
Time-Preserved Replay
Original timestamps preserved.
 
Accelerated Replay
Example:
100 alerts/minute
500 alerts/minute
1000 alerts/minute
 
Phase 7: Alert Enrichment
Purpose
Attach contextual information.
 
Asset Enrichment
Add:
•	Asset criticality
•	Asset type
•	Business function
 
Threat Intelligence Enrichment
Add:
•	IOC reputation
•	Confidence score
 
MITRE Enrichment
Add:
•	Technique ID
•	Technique name
•	Tactic category
 
Phase 8: Risk Scoring
Purpose
Calculate a context-aware risk score.
Wazuh severity should be one input, not the final score.
 
Inputs
•	Wazuh severity
•	Asset criticality
•	MITRE technique importance
•	IOC reputation
•	Alert frequency
•	Historical false positive rate
 
Output
Risk Score:
0–100
Example:
Failed Login
Severity 5
Criticality 4
IOC Unknown

Risk = 25
Example:
Credential Dumping
Severity 12
Criticality 10
IOC Malicious

Risk = 95
 
Phase 9: Alert Classification
Purpose
Reduce analyst workload.
 
Initial Categories
•	Likely Benign
•	Likely False Positive
•	Requires Investigation
•	Critical Incident
 
Initial Implementation
Rule-based classification.
Machine learning can be added later.
 
Phase 10: Alert Grouping
Purpose
Reduce duplicate investigations.
 
Example:
Raw alerts:
20 Failed Login Alerts
Host = DC01
Output:
Single Investigation
Grouping criteria:
•	Same host
•	Same user
•	Same rule
•	Similar timeframe
 
Phase 11: Prioritization
Purpose
Determine analyst review order.
Priority should be based on:
•	Risk score
•	Asset criticality
•	Threat intelligence
•	Alert classification
Output:
Ranked investigation queue.
 
Phase 12: Analyst Evaluation
Baseline Workflow
Analyst receives:
Alert 1
Alert 2
Alert 3
...
Alert N
Measurements:
•	Total alerts reviewed
•	Time spent
•	False positives encountered
 
Enhanced Workflow
Analyst receives:
Investigation 1
Investigation 2
Investigation 3
...
Investigation N
Each investigation contains:
•	Risk score
•	Classification
•	Asset information
•	Threat intelligence
•	Related alerts
Measurements:
•	Investigations reviewed
•	Time spent
•	Investigation completeness
•	Missed critical alerts
 
Success Metrics
Primary Metrics
•	Analyst workload reduction
•	False positive reduction
•	Prioritization accuracy
•	Classification accuracy
•	Investigation completeness
Secondary Metrics
•	Alert reduction percentage
•	Incident grouping effectiveness
•	Average risk score accuracy
•	Mean time to triage
 
Final Simulation Deliverables
The completed simulation should produce:
1.	Wazuh-generated alert dataset.
2.	Ground truth labels.
3.	Asset inventory database.
4.	Threat intelligence database.
5.	Replay engine.
6.	Alert enrichment module.
7.	Risk scoring module.
8.	Classification module.
9.	Alert grouping module.
10.	Prioritization engine.
11.	Analyst evaluation framework.
12.	Before/after workload comparison metrics.
After dataset creation, all research experiments should run entirely from the exported dataset and supporting databases without requiring the Windows VM or Wazuh environment.
